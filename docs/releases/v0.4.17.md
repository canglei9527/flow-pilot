# v0.4.17 发布介绍：语言一致性与 Token 优化

发布日期：2026-10-09 · 版本线：0.4.16 -> 0.4.17

## 一、这次发布解决什么问题

v0.4.16 及之前版本存在三类影响使用体验和成本的问题：

1. **中英文混排**：部分参考文档的标题和关键术语混用英文，影响中文用户阅读连贯性。
2. **逻辑矛盾**：MICRO 档位的文档目录创建条件在不同文件中描述相反；结构变更的迁移表填写时序说明存在矛盾。
3. **Token 浪费**：高频加载的 `fast-path.md` 包含低频使用的 UI 设计段落；两个 SKILL.md 的 `description` 字段包含大量重复触发词和功能说明。
4. **测试覆盖缺口**：`EVALS.md` 缺少文档整理路径和需求澄清门的验证场景。
5. **项目自身缺索引**：作为 DURABLE 档位项目，根目录缺少 `ai-context/INDEX.md`。

v0.4.17 修正所有语言一致性问题、消除逻辑矛盾、补全测试场景、优化 token 消耗，并为项目自身建立导航索引。

所有标题和关键术语统一为中文，保留代码标识符和技术名词的英文原文。

## 三、逻辑矛盾消除

### MICRO 档位文档目录条件统一

**问题**：`bootstrapper/SKILL.md` 的文档目录约定说"只有在用户明确要求单文件且不需要维护文档时，才不创建该目录"，意味着 MICRO 默认会创建 `文档/`；但 `workflow.md` 的 MICRO 章节说"若用户明确要求维护文档，则将其放入 `文档/` 目录"，意味着 MICRO 默认不创建。

**修正**：以 `workflow.md` 为准（符合 MICRO 一次性脚本的定位），修正 `SKILL.md` 为：`MICRO` 仅当用户明确要求维护文档时才创建 `文档/` 目录；用户明确要求单文件工具时不创建该目录。

### 迁移表时序说明修正

**问题**：`structural-change.md` 的迁移表说"在每个批准的迁移批次**前**填写"，但表头包含"旧实现删除证据"和"验证"列，这两列只有批次执行完第 5 步删除旧实现和第 6 步验证后才能填写。

**修正**：明确区分规划列和证据列的填写时机——"在每个批准的迁移批次**前**填写规划列，批次完成**后**补填证据列"。

## 四、Token 优化

### description 字段精简

**优化前**：
- `ai-project-maintainer`：约 65 词，包含"刷新后又出现""收尾阶段""验证并归档"等重复触发词，以及"Covers source, tests, build configuration..."功能说明段落。
- `ai-project-bootstrapper`：约 55 词，包含"新应用/网站/服务/接口/CLI/脚本/机器人"完整枚举列表。

**优化后**：
- `ai-project-maintainer`：约 30 词，删除重复触发词和功能说明，保留核心触发关键词。
- `ai-project-bootstrapper`：约 35 词，删除枚举列表，保留核心触发词。

`description` 字段用于触发匹配而非阅读，冗余内容在 SKILL.md 正文中已有完整描述。

### 移除 fast-path 中的低频段落

**优化**：将"设计改进和体验优化"段落（约 15 行）从 `fast-path.md` 的普通变更路径第 4 步中移除。该段落只在用户明确要求 UI 现代化时才有用，放在高频加载的快速路径文件中每次修 Bug 都要读取，造成不必要的 token 消耗。

该段落规则仍然有效，如需在结构变更或设计改进场景中使用，可按需添加到 `structural-change.md` 末尾或创建独立参考文件。

**预估节省**：每次加载 `fast-path.md` 节省约 15 行 + description 字段节省约 35 词 ≈ 减少 ~10-12% 的高频路径 token 消耗。

## 五、测试场景补全

`skills/EVALS.md` 新增两个验证场景：

### Documentation Migration: Idempotency And Trigger Guard

验证文档整理路径的关键边界：
- 只有明确命令才触发全项目 Markdown 扫描，普通 Bug 修复不触发；
- 识别已有规范目录（`docs/`）并复用，而不是新建 `文档/`；
- 跳过已在规范目录中的文件；
- 检测命名冲突（如根目录和 `docs/` 都有 `ARCHITECTURE.md`）并停止该文件，报告而非覆盖；
- 同一命令重复执行必须幂等：第二次执行时检测到无文件需移动，不产生进一步改动。

### Requirements Dialogue: Three-Option Gate Behaviour

验证需求澄清门三个选项的行为差异：
- **开始需求问卷**：每次只问一个影响实现的问题，动态补齐信息后给出总结并等待确认再开始。
- **跳过问卷**：不做结构化访谈，只有缺少执行必需信息时才补问，补齐后立即执行。
- **完全不问，直接执行**：采用合理假设立即创建文件并验证，不停在方案或"等待确认"阶段，项目根目录内写入不请求确认。

跨所有路径的共性验证：
- Bug 修复、只读审查、纯重构、仅配置调整时需求门不出现；
- "完全不问"不绕过项目根目录保护、密钥读取限制或任何更高级规则；
- 需求门不是 IDE 计划模式，不制造 IDE 审批步骤。

## 六、项目自身索引建立

**新建**：`ai-context/INDEX.md`

作为 DURABLE 档位项目（多人/多 AI 协作、多个稳定工作流），项目根目录应有任务→入口→聚焦测试的导航索引。新建索引覆盖 7 条主要路由：
- 修复现有项目 Bug → `ai-project-maintainer/SKILL.md`
- 结构重构 → `references/structural-change.md`
- 从零创建新项目 → `ai-project-bootstrapper/SKILL.md`
- 整理维护文档 → `references/documentation-migration.md`
- 需求澄清 → `shared/requirements-dialogue.md`
- 查看安装和发布流程 → `README.md`
- 运行结构检查 → `scripts/verify-maintainability.mjs`

索引格式遵循 `ai-context-format: 1`，包含审核日期元数据，提供可验证的真实测试命令。

## 八、升级影响

**无破坏性变更**。所有修改为文档修正、逻辑澄清和 token 优化，不改变 Skill 的触发条件、路由逻辑和验证规则。

**Token 优化收益**：
- 高频路径（Bug 修复、普通变更）每次节省约 10-12% 的参考文档 token 消耗；
- Skill 触发匹配阶段节省约 30 词的冗余 description 读取。

**测试覆盖提升**：
- 新增 2 个 eval 场景，覆盖文档整理路径和需求澄清门的关键边界条件。
