# 需求澄清门

本流程只适用于两类请求：创建新项目，或在已有项目中新增/扩展功能。修复 Bug、解释、审查、诊断、普通配置调整和仅重构不显示此选择。

## 开始前的三选一

先检查当前请求和同一任务的已有选择。用户已经说“直接做”“不要提问”或选择过某种模式时，沿用该选择，不重复询问；用户随后改变偏好时以最新明确指令为准。尚未选择时，在读取项目源码或创建文件前提供以下三个选项：

1. `开始需求问卷`
2. `跳过问卷`
3. `完全不问，直接执行`

这是可选的需求澄清，不是写入审批。等待期间可以整理已提供的信息；不要扫描无关工作区。尊重客户端的等待约定，给用户合理答复时间，不能把异步问题刚发出视为无人回答。若问题工具结束而无回答，且目标、范围与验收已清楚，可说明采用“跳过问卷”并继续已授权工作；必需信息或操作授权缺失时仍须等待，沉默不是授权。选项文字可以按客户端语言呈现，但含义必须保持一致。

## 1. 开始需求问卷

- 每次消息只问一个当前最影响实现的问题，并紧接着说明为什么需要这个答案。
- 只追问真实的信息缺口，不重复用户已经明确的内容，也不为了凑题数提问。
- 根据任务动态提问，不设固定题数。至少确认目标、范围、约束、验收标准和暂不处理项；如果其中一项已明确，直接记录，不再问一遍。
- 认为信息已经足够时，停止提问并输出理解摘要，摘要必须包含：目标、范围、约束、验收标准、暂不处理项，以及仍采用的明确假设。
- 摘要后等待用户确认。用户确认后才开始读取、创建、修改或验证；用户提出修正时，只围绕修正后的缺口继续澄清并重新总结。

## 2. 跳过问卷

不进入结构化的一问一答，也不等待理解摘要确认。根据用户请求和最小项目证据直接执行；只有缺少目标路径、技术栈、关键行为或验收条件等执行必需信息，导致无法安全开始时，才补问必要问题。补齐后立即执行，不把补问扩展成完整问卷。

## 3. 完全不问，直接执行

- 不再询问业务需求、实现方案、默认假设或摘要确认。
- 自行分析已有信息，采用合理且可验证的假设，立即读取最小相关上下文、修改当前目标所需的文件，并运行适用验证。
- 不停在方案、任务清单或"等待确认"；最终报告中说明实际采用的假设、完成的修改和验证结果。
- 此选择不扩大任务范围：只操作当前请求必需且已获授权的文件，保护用户已有修改、未跟踪文件和其他项目。文件位于工作区内不等于允许删除；工作区外的精确目标若已明确授权，也不重复请求确认。
- 删除用户文件、推送、发布、部署或其他外部动作仍需核对该具体操作是否已有授权；缺失时先准备可审阅结果，再询问缺少的授权。不把“完全不问”当作这些操作的统一许可。
- "完全不问"只控制本需求澄清流程，不授权读取或输出密钥，也不允许违反更高优先级的系统、客户端或项目规则。

## 与 IDE 计划模式的关系

需求澄清门不是 IDE 的计划模式，也不调用或替代它：

- `开始需求问卷` 的摘要确认是需求理解门；IDE 计划模式若存在，仍是客户端的执行计划门。
- `跳过问卷` 不额外创建需求确认门，IDE 是否显示计划由客户端既有行为决定。
- `完全不问，直接执行` 不主动进入或制造 IDE 计划审批，也不把"思考"改写成只输出计划；如果客户端或系统强制显示计划门，Skill 无法绕过该强制门，门解除后继续执行。

无论哪种模式，选择完成后都要遵守本 Skill 的项目根目录、读取范围、用户已有改动保护和验证规则。
